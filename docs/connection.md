# Соединение с рабочим сервером

## Причина

1 ноября 2026 года в рабочей сети воспроизведено зависание ответов `wlqwwhshqrqanapsnsik.supabase.co`: одинаковый запрос `POST /rest/v1/rpc/is_initialized` через HTTP/1.1 возвращал `200 true` за 0,99 с, а через HTTP/2 получал `200` и `Content-Length: 4`, но не получал тело до отмены через 12 с. Сервер Supabase имел статус `ACTIVE_HEALTHY`; в журнале запросы сайта завершались с `200` за 0,2–0,9 с. Это указывает на сбой передачи ответа между сетью и браузером, а не на потерю данных.

В браузере нельзя переключить версию HTTP через `fetch`. Увеличение таймера не восстанавливает зависшее тело ответа.

## Рабочий маршрут

`infra/connection` — отдельный сервис Vercel с внешними перенаправлениями запросов в ту же рабочую Supabase. Он не содержит функций, паролей, служебных ключей или своей базы. Адреса назначения закреплены в конфигурации; передать произвольный внешний сервер через параметр нельзя.

Рабочий адрес: `https://nlmo-api.vercel.app`. Проект `nlmo-api` (`prj_q5LJpthiMXyjGu4lVVdtbs9pFSxc`) находится в подключённой команде владельца сайта `jj1-ab03`. Сайт остаётся по адресу `https://timativ-blip.github.io/nlMO/`. В `.env.production` включена переменная `VITE_SUPABASE_GATEWAY_URL`; исходный адрес проекта Supabase не заменяется.

Кеширование всех ответов отключено, в том числе на CDN. Авторизация, ограничения строк и проверка ролей выполняются в прежней базе с прежним пользовательским токеном. Повторной отправки запроса при ошибке нет: потерянный ответ не должен приводить к повторному созданию записи.

Клиент подключает сервис только при заданной переменной сборки `VITE_SUPABASE_GATEWAY_URL`. Значение должно быть проверенным HTTPS origin созданного проекта, без пути, параметров и пароля. Оно не берётся из адресной строки или локального хранилища браузера. Без переменной сохраняется прямое подключение.

Исходный `VITE_SUPABASE_URL` и ключ локальной сессии `sb-wlqwwhshqrqanapsnsik-auth-token` сохраняются, поэтому существующий вход остаётся доступным. Через сервис идут Auth, REST, Storage и Edge Functions, включая Telegram и медиа. Подписанные ссылки вложений используют тот же маршрут. WebSocket остаётся прямым: он использует отдельное соединение с подтверждённым в журнале статусом `101`.

## Публикация

1. Использовать отдельный проект Vercel `nlmo-api` в аккаунте владельца сайта. Для обновления публиковать только каталог `infra/connection`, тип Other, пустые команды установки и сборки, каталог результата `public`. Платные дополнения не нужны. Первая публикация создана из этих двух файлов через API Vercel; автоматическая публикация из Git для этого проекта не настроена.
2. Опубликовать эти файлы и получить фактический постоянный адрес проекта. Не включать адрес в рабочем клиенте до проверки принадлежности проекта и успешного ответа сервиса.
3. Проверить через сервис `is_initialized`, CORS с origin сайта, отказ без авторизации, передачу 10 МБ без ограничения тела запроса функцией и отсутствие CDN-кеша. Проверять без создания тестовых бизнес-данных.
4. Только после этого задать `VITE_SUPABASE_GATEWAY_URL` в `.env.production`, проверить сборку и опубликовать GitHub Pages. Сам сайт остаётся по прежнему адресу.
5. Проверить обычный вход, восстановление сессии, приватные вложения и мини-приложение. Привязки Telegram и вебхук бота не меняются.

Для отката удалить переменную сборки и перепубликовать сайт; базу и пользовательские записи менять не требуется.

## Проверки

`npm run test:connection` проверяет передачу токенов и тела, отмену запросов, отсутствие повторных записей, ограничения маршрутизации и кеша, а также вход, чтение, файл 10 МБ, подписанную ссылку и вызов функции через используемую сайтом библиотеку Supabase. `npm run test:startup` и `npm run test:telegram` проверяют прежний запуск и бота. Сетевые заглушки не подтверждают доступность опубликованного сервиса: она проверяется отдельно после создания проекта.

Проверка опубликованного сервиса 1 ноября 2026 года: через HTTP/2 `is_initialized` возвращает `200 true` за 0,53–1,52 с, Auth health — `200`, функция Telegram — ожидаемый `405` на GET. Анонимное чтение профилей возвращает пустой набор, закрытый RPC бота — `401`/`42501`. CORS разрешает origin сайта и необходимые заголовки. Два повторных GET имеют `x-vercel-cache: MISS`, `Cache-Control: private, no-store, max-age=0` и `CDN-Cache-Control: no-store`. Полные 10 МиБ переданы в Storage; запрос с заведомо неверным JWT отклонён `AccessDenied`, файл не создан. Бизнес-данные и настройки бота при проверке не изменялись.

Документация: [внешние перенаправления Vercel](https://vercel.com/docs/routing/rewrites), [отключение кеширования](https://vercel.com/docs/routing/rewrites#disabling-caching-for-rewrites-to-external-origins), [настройка клиента Supabase](https://supabase.com/docs/reference/javascript/initializing).
